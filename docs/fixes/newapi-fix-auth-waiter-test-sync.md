# 认证等待队列测试同步修正

日期：2026-10-17。基线 `67506c8`。用户确认的测试同步修正已完成并通过本地验证；不改变生产认证、队列预算、业务契约或运行服务。

## 一 现象与复现

SGM-4 A 默认 debug 全量回归为 385 passed/1 failed/6 ignored，唯一失败是 `authentication_waiters_are_bounded_and_cancelled_login_opens_circuit` 在 `src/newapi/transport/tests.rs:715` 期望假服务收到 1 次登录，实际为 0。此前旧基线 `f0b8295` 也已复现；本轮修改前，现有测试二进制第一次复测再次得到同一断言失败（0.18 秒）。

最小复测命令：`cargo test --locked --offline newapi::transport::tests::authentication_waiters_are_bounded_and_cancelled_login_opens_circuit -- --exact --nocapture`。该问题依赖调度，单次通过不证明竞态消失。

预期是第 65 个请求被 QueueFull 拒绝，已经发出的唯一登录被取消后，后续等待者不再登录，64 个逻辑槽与 HTTP 在途槽全部回收。失败发生在验证这些语义的测试准备阶段，不是新账本函数调用了认证路径。

## 二 根因分析

测试仅将每个请求 future poll 1 毫秒，随后保存到 Vec，不再驱动首个 future。占用逻辑槽在 `send_fenced` 的首次 poll 内发生，而完成连接、发送和假服务读取属于后续异步步骤。短暂 poll 超时并不证明假服务收到登录；即使之后继续等待其他请求，停在 Vec 内的首个 future 也不会因此自动继续执行。

因此断言缺少请求到达的同步先决条件。增加固定 sleep 不能消除这个差异，本修正不采用它。

## 三 参考实现对照

这是测试协调错误，不是 NewAPI/GLM 算法错误，第三方算法对照不适用。依据仓库实际路径核对：`send_fenced` 先占逻辑槽，`refresh_session` 再等单飞锁，`refresh_session_locked` 获取 HTTP 预算后才发送登录；Fake 读完请求才记录调用。测试必须分别观测这些阶段，不能把前一阶段当作后一阶段已完成。

## 四 修复方案

仅改原测试函数：

1. 测试先持有既有 refresh 锁，逐个单次 poll 64 个请求，确定全部等待认证且假服务收到 0 次请求。第 65 个仍必须 QueueFull；该等待加安全超时防止错误实现挂住套件。
2. 释放测试持有的锁，持续 poll 第一个请求，直到 Fake handler 发出 Notify 到达通知；若请求提前结束或等待超过安全超时，测试失败。
3. 明确收到 1 次登录后取消首个 future，检查认证已熔断、下一等待者得到 AuthFailed、请求数仍为 1。
4. 释放其余等待者，严格核 64 槽全部可用和 HTTP 在途数为 0。保留原慢响应夹具，它不是到达同步条件。

在原用例内加入锁闸门，把过去概率性“已占槽但尚未发送”固化为确定性回归前置状态，不增加通用测试框架或生产注入点。

SGM-4 A 的机械脚本仅允许这一项测试函数作为独立修正例外；仍将该文件函数之外的内容与原基线逐字比较，其他生产源码零改动要求不放宽。

## 五 正确性论证

- 根因消除：Notify 只能由已读取登录请求的假服务触发；等待时持续 poll 登录 future，所以不会停在只占槽的状态。锁闸门还确保回归确实经历了该状态。
- 不变量保持：64 个等待请求和第 65 个 QueueFull、唯一登录、取消后熔断及槽回收断言保留，并加强具体 AuthFailed 检查。单次 poll 只用于确定性注册锁等待，不再用于推测网络进度。
- 无回归：修改限 cfg(test) 函数及校验脚本/文档；生产 transport、Fake 公共实现、依赖、业务模块均不改。用默认并发全量回归与独立性能入口核验，不降低并发或放宽预算。

五维度复核：一致性上保留原认证不变量；风格上只使用现有 Notify 与标准库 poll_fn；正确性由确定性阶段断言及两项变异核验；性能上移除 64 次固定短等待，不增加生产开销；可维护性上只改原测试函数，没有新增生产注入点或测试框架。SGM-4 A 生产代码未改，其原独立契约审核结论继续适用；本修正按 workflow §5.2 自审，不冒称重新做了独立代理审核。
