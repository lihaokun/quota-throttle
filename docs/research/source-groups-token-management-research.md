# 来源共享 分组路由和用量面板方案

更新日期：2026-10-14。状态：产品范围按最新讨论更新，原生接口隔离验证通过，架构待评审。本分支新增设计文档和隔离测试探针，不修改业务代码或生产配置、数据库、渠道、令牌和进程。

本轮交付：[实现前审核](../design/source-groups-token-management/review.md)、[架构稿](../design/source-groups-token-management/architecture.md)、[实施准备计划](../design/source-groups-token-management/implementation-plan.md)。其中列出 11 项原生接口实测、58 项既有测试结果及尚待实现的边界，不以探针通过代替新功能验收。

## 当前范围和已取消的方向

面板调整为三个一级页面：来源管理、分组与 Key 管理、数据。来源是唯一的真实上游资源，可以加入多个同类型的组；每个组独立维护首选渠道和优先级，来源的流量、token、异常与额度状态统一计算。

每把下游 NewAPI 访问 key 只对应一个组，每个组只对应一种来源类型：GLM 或火山。每把访问 key 同时支持 OpenCode 的 OpenAI 格式与 Claude 的 Anthropic 格式，协议不决定分组；使用者只拿 key 和接入地址，不需要面板账号。

已取消“每把访问 key 独立绑定上游”和“按访问 key 绑定数均匀分配”。火山与 GLM 都采用组内一个首选来源的路由结构，但调度规则不同。没有为了持久绑定而维护定制 NewAPI 的既定决定；优先使用原生分组、渠道 priority 和请求重试。

GLM 原有 95% 预防、降级、restore、粘滞、临期和手动固定策略不变。火山没有临期概念、不按重置时间选源、不显示临期 tag。

## 来源与组内渠道的关系

| 对象 | 职责 | 关系 |
| --- | --- | --- |
| 来源 Source | 上游类型、凭据、地址、模型目录、全局启停、用量与异常 | 一份主记录，可以被多个组使用 |
| 分组 Group | 类型、来源成员、组内活动源、固定偏好与优先级 | 只接收同类型来源，可以签发多把访问 key |
| 组内渠道 Membership | 某来源在某组中的 NewAPI 渠道与 priority | 每个 source_id 与 group_id 组合最多一条有效关系 |
| 访问 Key | NewAPI token，供客户端调用 | 一个 token_id 对应一个分组，不固定到某个来源 |
| 消费或异常记录 | 某次实际调用及其归属 | 保留 source_id、channel_id、group、token_id、model 和时间 |

类型取自来源配置，不按模型名称推断。火山来源即使提供 glm-* 模型，也仍是火山来源；GLM 类型的组不能加入火山来源。

### 推荐复制渠道 不复制来源

NewAPI 渠道的 group 可以列多个组，但 priority 是渠道上的一个值。若两个组直接共用同一个 channel_id，就不能为该渠道分别设置不同优先级。[渠道结构](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/model/channel.go#L23)

因此推荐给每个来源与组的关系创建一条独立渠道：

| 真实来源 | 组内渠道 | 分组 | 示例 priority |
| --- | --- | --- | --- |
| 火山来源 S | 渠道 S-A | 火山组 A | 100，A 组首选 |
| 同一个火山来源 S | 渠道 S-B | 火山组 B | 10，B 组备用 |
| 火山来源 T | 渠道 T-B | 火山组 B | 100，B 组首选 |

S-A 与 S-B 使用相同来源的上游凭据、地址和模型配置，只是 group、priority 等路由属性不同。来源 S 只有一份额度、失败计数与周期状态，不能因为加入两个组就多出一份额度。

来源对象先于组存在。新增来源可以暂不加入任何组；加入组时才创建或复用对应的组内渠道。界面只需“把来源加入组”，不要求管理员手工复制凭据。

不能直接裸调用 CopyChannel 后再慢慢修改：当前版本会继承原渠道的 group、priority 和 status，可能暂时在原组产生第二条已启用的高优先级渠道。推荐按来源模板明确创建新渠道，初始化为目标组和禁用状态，对账映射及配置后再启用；复制只是逻辑复用方式，不等于无条件调用复制接口。[复制实现](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/controller/channel.go#L1353)

### 哪些独立 哪些共享

- 组内首选、priority 和 GLM 的 pin 属于组内渠道关系；调整 A 组不能重写 B 组的 priority。
- 来源凭据、地址、基础模型目录、GLM 用量探针结果、火山每日 token 上限、重置规则、失败序列和耗尽原因属于来源主记录。
- 来源暂停或耗尽会排除所有组内对应渠道。这是共享资源的正常影响，不与“组内优先级独立”矛盾。
- 从某组移除来源，只退役该组的成员关系和渠道，不删除来源，也不影响其他组。
- 在来源页删除来源，要先列出受影响的组并确认，停止所有相关渠道的后续路由；保留来源和渠道的历史归属以支撑统计。是否物理删除 NewAPI 渠道留待细化，但不得留下继续接流量的孤立副本。
- 来源凭据或模型目录更新统一同步到所有有效成员渠道。组内副本不允许独立修改上游凭据或地址而仍冒充同一个来源。
- 同一真实凭据不应通过重复创建来源绕过共享额度。优先复用现有来源；重复识别使用服务端敏感指纹等方式，不把明文 key 写入日志。
- 共享来源不代表上游额度互相独立；不同来源如实际共享同一供应商团队额度，也不能把探针返回的剩余额度简单相加。

## 三个页面

### 页面一 来源管理

统一新增、删除、启用和暂停来源。新增时必选 GLM 或火山类型，录入名称、备注、上游凭据、地址、模型发现和鉴权配置；展示被哪些组使用。

GLM 来源显示现有额度窗口、查询错误和临期标签，沿用原数据语义。来源全局启停是管理动作，不改原有阈值算法；GLM 固定到某源的操作放在具体组上下文中。

火山来源在原 GLM 额度位置显示：

- 可用、停用或耗尽状态，以及具体耗尽原因。
- 下一次重置时间和倒计时，不显示临期标签。
- 本周期全模型输入与输出 token 合计、配置的每日上限及进度。
- 每个模型的请求记录数、输入 token、输出 token 和总 token。
- 连续失败次数及阈值，以及“撤销错误判定”按钮。

编辑界面可修改每日 token 上限、失败阈值、重置时刻和时区。默认每日 01:00、UTC+08:00；token 上限留空表示不启用上限判据，不虚构默认额度。

暂停是来源级操作，影响它的全部组内渠道；同步未完成或部分失败时显示处理中/失败明细，不能提前显示“所有组均已暂停”。已发出的在途请求不被描述为已撤销。

### 页面二 分组与 Key 管理

同一个一级页面内管理分组、组内来源和访问 key，不再为访问 key 单独占一个一级页面。

分组部分：

- 新建组必选类型；同类型可有多个组。
- 从来源库加入已有来源，只允许类型匹配，不复制来源主记录。
- 展示组内渠道、首选/备用、priority、来源全局状态及配置同步状态。
- 移除组成员只影响当前组。来源本身的暂停和耗尽不能被组内启用开关覆盖。
- 每组独立选择首选；GLM 保留原固定/取消固定逻辑，火山使用下文的组内首选策略。

访问 key 部分：

- 查看现有 key 的名称、掩码、所属组、状态、创建时间和有效期。
- 支持生成、按需复制、启用、禁用和删除；生成必须指定一个组，首版不用 auto 跨组路由。
- 同一把 key 提供 OpenCode 与 Claude 两套接入信息。删除访问 key 不删除来源或分组。
- 旧 token 的 group 为空时显示“继承账号组”，不擅自改组或重签。
- 显示跟随所属组调度，不再展示已经取消的逐访问 key 上游绑定关系。

### 页面三 数据

展示当前整体用量和每把下游访问 key 的用量，沿用现有用量图的近 24 小时、近 30 天和按天进入小时明细的交互。可用同一图表切换“整体”与指定访问 key；每个 key 的历史用 token_id 关联，不用可改名或可重复的 token_name 当主键。

柱形图推荐改为按模型分色的堆叠柱：

- 横轴仍是时间，每个时间桶内各颜色段分别表示一个模型的 token 总量，整根柱子的高度等于该桶全部模型的总量。
- 图例可筛选模型；悬停显示模型分项、输入/输出、合计和请求数。颜色在同一模型跨时间、整体/单 key 视图之间保持一致。
- 顶部整体 token、每 key 汇总和图表必须使用相同时间区间与统计口径。
- 共享来源只统计实际发生的消费，不能把“来源总量”和“各组子总量”再次相加。
- 保留已删除 key 的历史标识；未纳管或无法归属的历史流量明确显示为其他/未归属，不静默漏掉。
- 完整数据中的空桶可以显示零；采集中、缺数据或查询失败不能伪装成零用量。
- 数据页自然日图表的时间区间与来源每日 01:00 重置周期分开标注；两者只有选择同一区间时才能直接比较，不能把午夜换日当成来源重置。

仅把现有单色柱子换颜色不够。当前 aggregate_usage 将数据拆成“小时总量”和“全时段模型总量”，丢失了时间与模型的联合维度。新结果必须保留至少“时间桶、模型、token 数”，单 key 视图还需要 token_id，不能从两份边际汇总倒推出每小时的模型分布。[现有聚合与图表](../../src/status.rs)

## 组内首选与跨组共享状态

### GLM 保持原策略

GLM 每组仍使用原有 active、pin、95% 预防线、全员越线后的降级档、restore、粘滞和临期优先规则。策略接收当前组的来源成员及它们的共享额度快照，下发到该组成员渠道；相同输入下原算法行为不变。

同一来源加入多个 GLM 组时，用量探针按来源采集一次，多组复用结果，不按渠道副本重复查询。只有首选、固定偏好与渠道 priority 是组级的；真实配额不是组级复制品。

不将火山的三态、错误阈值、每日 token 上限、定时恢复或无临期逻辑套进 GLM。

### 火山每组一个首选来源

火山组维护一个正常首选源，例如首选渠道 priority=100、备用=10。每把访问 key 跟随所属组的渠道优先级，不单独持有来源绑定。

首选仍可用时保持不变。首选暂停、耗尽或从组移除后，在本组可用成员中选下一个首选；建议采用稳定轮转顺序，不按重置时间排序。这里不再承诺“访问 key 绑定数均匀”，也不要求不同组的首选来源一定不同。

NewAPI 普通路由先筛选组和请求模型，再比较渠道 priority。首选不支持某模型时，可以使用本组其他支持该模型的渠道；整组不支持时返回错误，绝不静默更换模型或跨组。此前基于“已绑定源”的拒绝条件随取消独立绑定而不再适用。[组与模型筛选](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/model/channel_cache.go#L108)

priority 表达首选，不是绝对锁定：单次失败允许按 NewAPI 允许的规则重试备用。只有源级耗尽判据成立，才排除该来源的所有渠道，并让受影响的组分别持久切换首选。重置或人工恢复仅让来源重新成为备用候选，不抢占各组仍可用的首选。

单个渠道只属于一个管理组，因而不同组可以独立改 priority；同一个 SourceId 可以拥有多个 channel_id。不要用一个 channel_id 的 group 填多个组来模拟独立优先级。

已有的亲和规则、指定渠道和其他路由约束可能覆盖普通优先级路径，隔离验证必须确认受管火山流量不被其改变；不为解决这一点修改 GLM 原行为。

## 火山源状态与 token 上限

### 两种耗尽原因

火山暂不做积分或价格换算。外部仍只有“停用、可用、耗尽”三个业务状态，内部单独记录两个原因，可以同时成立：

1. 连续上游不可用，默认 3 个独立请求，可配置。同一真实来源跨所有组共享连续失败序列，同一请求在同源内部的重试不重复计数；该来源一次成功调用清零失败计数。在另一个来源重试成功，不清除原源的失败。
2. 当前重置周期累计输入加输出 token 达到配置上限。跨所有组、所有访问 key、所有模型合并计算，不给每个渠道副本重新分配额度；缓存若已包含于输入 token，不额外累加。

规则 1 只统计归因于上游来源的有效失败。下游 key 鉴权错误、客户端参数错误、超上下文、主动取消、NewAPI 管理接口限流和单个组的配置错误不直接算来源不可用。错误分类与流式完成条件要在细化中明确，不能只统计任意非 200。

失败事件经 channel_id 映射到 SourceId 后幂等消费，保留原组与 token 维度作为诊断明细。达到阈值后锁存错误判定，迟到成功不自动撤销。

### 人工撤销与状态优先级

- 手动停用优先：无论是否存在耗尽原因，都保持停用。
- 未停用但任一耗尽原因成立时为耗尽；两类原因均不成立才可用。
- “撤销错误判定”只清规则 1 及失败计数，不删除 token 用量，不清规则 2，不解除手动停用。撤销前的重复或迟到事件不得立即恢复同一错误判定。
- 修改 token 上限立即重新评价规则 2；提高后不再达限且没有其他原因可恢复，降低到已用量以下立即耗尽。该操作不清规则 1 或手动停用。
- 业务状态在来源主记录统一维护，再同步到全部有效成员渠道；部分渠道失败时不能假装整体完成。
- NewAPI 自动禁用不能未经协调就把一个副本的单次错误当成整个来源已经连续失败 3 次。状态同步必须明确唯一写入归属，避免原生自动禁用与重置相互覆盖。

### 每日重置

默认每天 01:00、UTC+08:00，管理员在来源编辑界面修改时刻及时区。重置清除上一周期的两类耗尽原因及失败计数，开始新的统计周期；手动停用不自动解除。火山不产生临期标签。

修改重置规则时，先处理旧规则已到期的重置，再计算严格晚于保存时刻的新边界；不额外立刻恢复耗尽、不清空已有用量、不移动当前周期起点，历史周期保持原边界。

持久化来源状态、两类原因、计数、周期、操作版本和重置规则。重启后补处理错过的周期；重复重置幂等，旧周期事件不得覆盖新周期或人工撤销后的状态。当前在途请求和历史统计不按各组副本分别重置。

### 上限是监测阈值

用户已接受按本 NewAPI 观测到的消费累计，在达到阈值后停止向该来源分配新请求。并发、日志延迟和来源状态扇出到多个渠道的延迟可导致超出，不承诺严格硬限额；规则 1 独立兜底上游不可用。

每日上限留空则只启用错误判据。用量缺失不是零，也不能以 NewAPI 的 quota 记账值代替真实 token 数或火山积分。其他地方直接使用同一上游 key 的消费不保证被本系统观测。

## 统一事实数据与图表聚合

消费和异常只采集一份事实记录，按不同维度形成视图：

- 来源视图：聚合映射到相同 SourceId 的全部渠道。
- 分组视图：按日志记录的实际调用组或历史成员关系聚合。
- 访问 key 视图：按 token_id 聚合。
- 模型时序：按时间桶和 model 聚合，可叠加上述筛选。
- 整体视图：对原始去重消费记录求和，不把多个视图互相叠加。

源周期 token 和失败判据使用统一事实，不以复制渠道的 used_quota、余额字段或当前 priority 推断；不同组可以分开查看用量，但共同消耗同一个来源上限。

消费按稳定日志 ID 去重。失败序列按实际来源与独立请求归并，保留结果顺序；不能因为一次调用出现在多个页面就重复计算。只采集所需元数据，不保存请求内容或完整凭据。

channel_id → SourceId 的映射要持久化，包含退役成员渠道。不得将旧 channel_id 改认成另一真实来源，否则历史会被重记。来源、组成员或访问 key 删除/改名后，历史仍按发生时的身份与归属统计，而不是按当前组成员表回推。

建议以统一的完整消费记录作为可对账的数据基础，保留时间、模型、访问 key 与来源维度；现有整体汇总与 flow 结果可辅助展示和核对，但不能再逐小时乘以每个 key 请求接口来拼时序。

初始回补与周期采集要有请求预算、超时、检查点和完整性标记，优先让出 NewAPI 管理调用预算给来源暂停/恢复及组内 priority 更新。多个页面和浏览器共用后端采集，不按来源数、成员渠道数或模型数启动独立轮询。

源周期使用半开区间，按实际记录记账时间归属；跨边界长请求不宣称与上游计费精确相同。历史未补齐、日志被关闭/清理或流式消费未记录时，显示数据缺口。只有相同范围且完整的记录，才要求模型分项合计等于图表总量。

## NewAPI 管理能力与安全边界

分组管理仍需同时对账渠道归属、分组注册和账号可用组。原生 /api/group/ 是查询接口，不是完整分组 CRUD；设置更新读取后合并，保留其他组和倍率。[分组说明](https://docs.newapi.pro/zh/docs/guide/feature-guide/admin/group)、[分组鉴权](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/middleware/auth.go#L420)

访问 key 的生成、列表、复制、启停和删除复用 NewAPI 令牌接口。列表是打码值，完整值按需读取；当前创建接口不直接返回新 token ID，不能靠“最新一条”认领并发创建结果，也不能盲目重试未知结果。[Token 接口](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/controller/token.go)

NewAPI 当前版本管理员所属 token 有指定渠道的特殊能力。管理员管理 key 不等于要把管理员所属 token 原样发给使用者；候选方案仍是在后端托管非管理员调用身份，面板统一管理，使用者只收到 key，不需要注册账号。签发身份、旧 token 兼容与额度校验需在细化中落定，不擅自重签存量 key。

面板继续作为可信本机管理面。管理员凭据不下发到浏览器，来源 key 与访问 key 默认打码，明文复制禁止缓存和日志记录，名称/备注/模型名按文本渲染。远程开放认证属于另外的部署约束。

## 当前基线与迁移约束

研究分支基于 origin/main 的 0b89c96；部署二进制 415e53e 的业务代码与其一致。原工作目录五个旧改动的备注链路及 glm-5.3 / glm-5.3-flash 示例已随 PR #1 的 9e14e66 合入，不重复覆盖新版模型发现。

迁移时将现有每把上游 key 建立稳定 SourceId，原渠道映射为该来源在 default 组中的成员渠道，保留渠道 ID、访问 token 和客户端 URL。新增其他组引用同源时才创建额外渠道；GLM 原算法只获得当前组来源及共享快照，不改变规则。

来源/模型发现成功结果仍权威，失败保护存量；基础目录按来源发现一次，再同步到各成员渠道，不按副本反复探测。全局源状态优先于组内首选，不允许组控制器把暂停副本重新打开。

新建组成员采用“记录创建意图 → 明确目标组创建禁用渠道 → 保存映射并核对 → 按来源和组状态启用”。超时先对账，不重复建渠道。源状态同步、成员配置同步和 priority 控制要区分所有权，避免整对象 PUT 覆盖别组配置。

生产部署前在独立端口、独立数据库和假上游验证；不拿真实 key 做错误注入。部署、重启及回退窗口另行确认。回退不自动删除新来源或访问 key，必须先处理新增组成员渠道的可路由状态。

## 必须覆盖的验收场景

- 同一 SourceId 加入两个同类型组，生成两个 channel_id；A 组为首选、B 组为备用，单改 A 的 priority 不改 B。
- 同源跨组并发消费合并进入一份每日上限，消费记录不重复计数；跨组失败和成功进入同一来源序列，诊断仍能按组筛选。
- 全局暂停/删除来源影响所有有效副本；组内移除来源只影响该组。部分同步失败明确可见，未完成不得声称全局停用成功。
- 火山两个耗尽判据独立，人工只撤销错误原因，不能绕过上限或停用；每日重置幂等，不抢占各组有效首选。
- 新建副本不短暂加入旧组、不继承旧组活动优先级造成双首选；来源配置修改同步所有副本，退役映射保留。
- 下游访问 key 只属于一个组，组只有一种类型；拒绝混类型加入。同一访问 key 同时走 OpenAI/Anthropic 协议且组权限一致。
- GLM 的原额度、95%/降级、restore、粘滞、临期与 pin 决策回归不变；火山完全没有临期 tag。
- 整体图和单 key 图均有模型分色，时间桶模型分项之和等于该桶总量；同名不同 token_id、改名和删除历史不串账。
- 两个组消费同源时，整体统计不把来源总量与组子总量重复相加；取消组成员后历史仍归原组、原来源。
- 超过 100 条、多页、重叠窗口、重复/迟到日志、记录缺口、重启续采和时区边界都能对账；多页面不成倍增加采集。
- 检查已有亲和/指定渠道规则、原生自动禁用与我们的来源控制是否冲突；不得靠直接写生产数据库或重启掩盖不一致。
