# 来源分组和访问 Key 管理调研与候选方案

日期：2026-10-13。状态：候选方案，待用户确认；不是已批准的架构或实施计划。

本功能让不同的 NewAPI 访问 key 使用指定的上游来源池，并在 quota-throttle 面板里管理来源组、组内上游 key 和下游访问 key。推荐复用 NewAPI 原有分组与令牌管理能力，不增加一层推理代理。每个来源组必须选择 GLM 或火山类型；类型只有两种，但允许建立多个同类型的组。

本次仅涉及调研文档和独立 Git 分支，不修改生产配置、渠道、令牌、数据库或进程。

## 已确认的使用方式

管理员在我们的面板选择来源组、生成或撤销访问 key，再把访问 key 和对应客户端的接入地址交给使用者。使用者只配置自己的 OpenCode 或 Claude，不需要注册账号、登录面板，也不需要管理来源组。签发身份和组权限由后端处理，不增加使用者的操作步骤。

每把访问 key 同时支持 OpenAI 与 Anthropic 两种下游请求格式，不提供“OpenCode 专用 key”或“Claude 专用 key”选项。同一个 key 的来源组与允许模型集合不随请求协议改变。协议入口共用凭据，不等于所有上游都已通过 thinking、tools、stream 等参数兼容验证；这些仍需按具体上游验收。

## 需求边界和术语

| 对象 | 含义 | 候选约束 |
| --- | --- | --- |
| 来源组 | 一组上游渠道，如智谱主组、智谱备用组、火山组 | 名称独立于类型；每组必选一个类型 |
| 来源类型 | GLM 即智谱 Coding Plan，或火山网关 | 决定接入配置、额度能力和管理策略，不由模型名称推断 |
| 上游 key | 智谱或火山提供的凭据 | 首版每把受管上游 key 对应一个渠道、归属一个来源组 |
| 访问 key | 发给 OpenCode、Claude 等客户端的 NewAPI token | 首版明确绑定一个来源组；同一组可签发多把访问 key |
| 请求格式 | OpenAI 或 Anthropic API 协议 | 与来源分组独立，不创建 OpenCode 组或 Claude 组 |

用户所说的“类型 1、类型 2”是业务分类，不是 NewAPI 渠道类型码。火山组也可能提供 GLM 模型，不能把 `glm-*` 模型名自动归到智谱来源。

普通路由的目标关系是：

```text
访问 key A ── 指定智谱组 ── 智谱渠道集合 ── 智谱上游 key
访问 key B ── 指定火山组 ── 火山渠道集合 ── 火山上游 key
```

这次不默认加入跨组自动兜底；组内没可用渠道时应如实报错，不能悄悄消耗另一个来源池。管理员调试凭据的特殊权限另见“权限和密钥安全”。

## 当前项目的基础和缺口

调研基线是最新 `origin/main` 的 `0b89c96`。本地部署二进制 `415e53e` 的业务代码与其一致；原工作目录保留在较旧的 `main`，不作为新功能基线。

原工作目录显示未提交的五个文件已经完成内容对照：备注字段、持久化、运行时传递、面板显示以及示例中的 `glm-5.3` / `glm-5.3-flash` 均已随 PR #1 的 `9e14e66` 提交进入本分支。无需重复应用旧补丁，尤其不能用旧的静态模型配置覆盖现有 `/models` 权威目录语义。原目录的本地改动保持原样。

| 已有能力 | 可复用部分 | 需要变化的部分 |
| --- | --- | --- |
| 智谱额度查询 | 5 小时和周窗口，兼容 token 型与积分型套餐 | 仅供 GLM 类型使用，不能要求火山 key 通过智谱探活 |
| 自动选择与固定 | 95% 预防线、全员越线后的降级档、粘滞、临期优先 | 从全局状态改成各组独立状态 |
| 渠道创建和对账 | 每把上游 key 一个渠道、GET 后局部更新 | 全局渠道模板改为按组选择模板及鉴权配置 |
| 模型目录 | 每把 key 的 `/models` 结果权威，失败时保护存量 | 各组保留独立目录；不能把组内并集写给每个渠道 |
| 面板统一采集 | 一次请求日志查询推导多渠道实时指标 | 多页面共用同一后端采集结果，不能每组启动重复轮询 |
| 管理请求认证 | `send_management` 处理会话过期和单次重登 | 新的 token 和分组操作复用该入口 |

## NewAPI 原生能力核实

官方文档明确区分用户分组、渠道分组、令牌分组，令牌可以指定渠道组；`auto` 才是跨组选择的特殊模式。[分组管理](https://docs.newapi.pro/zh/docs/guide/feature-guide/admin/group)

以下源码核对固定在配置所用 NewAPI `v1.0.0-rc.20` 对应提交 `6ce7305cd36f16506fb6a2c3c524a5a318539ba7`，避免把最新文档中的全部功能直接套到本地版本。

### 分组和模型共同限定渠道候选

渠道缓存按 group、model 建索引，再按 priority 排序；指定一个普通组不会因为另一个组存在同名模型就自动跨组选择。NewAPI 渠道本身可以挂多个组，但本项目首版建议每个受管渠道只归属一个组：渠道的 priority 是单值，多组共用同一渠道会让两个调度器互相覆盖。[渠道候选源码](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/model/channel_cache.go)

固定来源的访问 key 应设置明确的 `group`，不使用 `auto`，也不启用跨组重试。跨组重试字段在该版本仅对 `auto` 有效。[组选择源码](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/service/channel_select.go)、[Token 数据结构](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/model/token.go)

### 新组不能只写一个名字

令牌鉴权同时检查所属账号是否有权访问目标组，以及该组是否在 NewAPI 分组倍率设置中注册。只改 `channel.group` 和 `token.group` 可能导致 403。创建来源组必须对账分组注册、账号可用组、渠道归属，再开放令牌创建；更新设置采用读取后合并，保留既有倍率和其他组的权限。[鉴权检查](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/middleware/auth.go#L420)、[可用组计算](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/service/group.go)

`GET /api/group/` 从倍率配置列出组名，不是独立的分组 CRUD 服务。因此 GLM/火山类型、组显示名称和上游配置仍由 quota-throttle 持久化管理，再映射到 NewAPI group。[分组接口源码](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/controller/group.go)

### 访问 Key 管理接口已有

| 功能 | 当前版本接口 | 重要约束 |
| --- | --- | --- |
| 分页列表 | `GET /api/token/` | 返回当前登录账号名下 token，key 已打码 |
| 读取单项 | `GET /api/token/:id` | 仍是打码结果 |
| 生成 | `POST /api/token/` | NewAPI 生成密钥；响应只有成功标记，不直接返回新 ID 或密钥 |
| 查看完整 key | `POST /api/token/:id/key` | 单独的敏感读取，有限流和禁缓存处理 |
| 修改或启停 | `PUT /api/token/` | 更新前保留额度、模型限制、有效期等其他字段 |
| 删除 | `DELETE /api/token/:id` | 校验所属账号，删除的是访问凭据，不是上游渠道 |

依据：[官方 Key 管理说明](https://docs.newapi.pro/zh/docs/guide/feature-guide/user/token)、[接口注册](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/router/api-router.go#L232)、[Token 控制器](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/controller/token.go)。

创建后不能直接取“列表最新一条”当成本次生成的 key；并发创建或超时重试会认错对象、生成重复 token。后续细化需要确定唯一关联方式与不确定结果的对账流程。本项目也不应为此直写 NewAPI 数据库。

## 候选方案比较

| 方案 | 收益 | 代价和适用范围 |
| --- | --- | --- |
| A 只在 NewAPI 原生管理页操作 | 改动最少，可立即人工配置分组和令牌 | 我们的面板仍不支持多组，智谱调度器仍是全局单池；不完整满足需求 |
| B NewAPI 负责路由和令牌，本项目负责来源组和面板 | 复用现有转发、鉴权、模型筛选、令牌生命周期；客户端地址不变 | 需改为组内调度，新增来源组和访问 key 的控制面；推荐 |
| C 新增推理代理，自建分组与密钥系统 | 可以完全自定义路由 | 重复实现 SSE、工具调用、鉴权与重试，扩大维护与安全负担；当前需求不需要 |

推荐 B。首版沿用现有 Rust 单进程及面板技术；页面数量增加不构成引入独立前端工程、插件框架或新数据库的理由。

## 候选面板布局

保留两个一级页面，通过来源组详情组织组内操作。

### 来源分组页

- 列出各组名称、类型、上游 key 数量、启用情况、模型目录状态；GLM 组额外显示活动 key 和额度。
- 创建组必须选择 GLM 或火山类型；可有多个 GLM 组或多个火山组，不把类型硬编码成两个固定分组。
- 进入组详情后提供“上游 key”“模型”“设置”三个页签。
- 上游 key 页支持新增、查看状态和备注；GLM 组保留固定、取消固定、额度和临期显示。停用与恢复需结合已有暂停问题另行明确，不能继续把“移出配置”包装成可恢复暂停。
- 模型页按每把 key 的发现结果展示，组级列表只是汇总；可手动刷新。若加入人工补充/排除，需与发现结果区分并标明人工条目的验证状态。
- 设置页编辑显示名称、上游地址、模型发现和推理鉴权；组内已有 key 时不允许直接把来源类型从 GLM 改成火山。

### 访问 Key 页

- 列表显示名称、掩码、所属来源组、启用状态、创建时间、有效期；分页和按组筛选。
- “生成 key”要求名称和来源组；有效期、额度、模型限制可放在高级选项，沿用 NewAPI 语义。
- 同一访问 key 提供 OpenCode 和 Claude 两套接入信息供管理员复制分发；不为两种协议再各建一把 key。
- 提供按需复制、禁用/启用、删除；删除必须确认目标。删除访问 key 不删除组、不删除上游 key，也不改变其他访问 key。
- 展示旧 token 的有效组：当 `group` 为空时标记“继承账号组”，不能显示成无组后擅自迁移。
- 访问 key 首版由管理员统一管理本服务托管的 token，不扩张成用户注册或全站账号管理。NewAPI 列表接口按登录账号隔离；若后端采用独立签发身份，需要通过相应身份读取新 token，并兼容展示现有管理账号名下的旧 token，写操作必须定位真实所属身份。

## 两种来源类型的不同处理

### GLM 类型

沿用智谱 Coding Plan 的额度探针、selector、阈值、粘滞、临期与降级规则，但在每个来源组内单独计算。某组全员超过 95% 只能改变该组的降级状态，不能影响另一组；固定 key 也必须带组上下文并验证归属。

不在本次顺便调整既有调度阈值。当前相同团队下多把 key 可能共享额度；按组展示不能暗示它们的额度可以相加。

### 火山类型

首个接入对象按此前提供的自定义 `*.apigateway-cn-beijing.volceapi.com/v1` 网关评估，不等同于官方方舟或火山 Coding Plan。

历史实测仅确认过该网关 `/models` 支持原始 `Authorization` 并返回模型列表；不能据此承诺推理请求、thinking、tools、流式调用的参数完全一致。`ModelDiscoveryAuth` 只影响发现请求，而 NewAPI 的 OpenAI/Custom 推理适配器默认加 Bearer，推理鉴权要单独配置并验证。[既有实测记录](model-catalog-research.md)、[推理鉴权源码](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/relay/channel/openai/adaptor.go#L162)

候选首版不调用智谱 quota 接口查询火山 key，不展示虚构的 5 小时/周百分比。没有经过确认的额度接口时显示“额度不可查询”；NewAPI 观测到的消费记录与上游套餐剩余额度分开展示。

组内优先复用 NewAPI 的 priority/weight 和允许的失败重试。上线前核对该网关的限额错误、重试配置和候选选择，不能承诺每一种 429 都会自动切换。长期冷却、主动探活恢复、额度预防切换是额外能力，不在此处视为已经解决。

火山 APIG 官方确实有按消费者、多时间窗口配置 Token 限流的能力；这不等于持有一把调用 key 就能查询该自定义网关剩余额度，也不能推广成所有火山产品均无查询接口。[APIG Token 限流说明](https://docs.volcengine.com/docs/apig/Implementing_token_rate_limiting_across_multiple_time_windows_with_APIG?lang=zh)

## 不应回归的约束

1. 每个受管渠道只有一个调度归属；组 A 的固定、停用、阈值或探针失败不改组 B 的 priority。
2. 面板各页共享后端采集快照；模型发现不加入周期轮询，访问 key 列表按需加载，完整密钥不做后台轮询。
3. 上游模型目录按 key 独立维护；发现失败保护存量，不能把其他组的模型写进该渠道。
4. 单个慢 quota 请求不能拖住所有组的控制操作。已有 2026-10-07 固定操作被串行查询拖慢约 35.7 秒的案例；后续设计需给采集与控制分配独立的等待边界，但不能为求快直接绕过额度安全校验。
5. 本地配置和 NewAPI 不是一个事务。创建组、建渠道、生成 token 等部分成功不能被显示为全部成功；必须能对账和重试，且不重复创建对象。
6. 接口超时不得被解释为操作未发生。令牌生成尤其不能盲目自动重试；删除或启停后需要确认最终状态。
7. `priority=0` 不是禁用渠道；“停止使用”必须明确是否修改渠道 status，不能再用低优先级代替停用。
8. 不能把全局用量历史图简单过滤成组级准确历史。现有 `/api/data/` 聚合已丢失渠道维度；首版只做有可靠来源的组指标，完整组级历史另行确定数据来源。

## 权限和密钥安全

NewAPI 管理账号凭据始终留在服务端。上游 key 与访问 key 在普通列表中都不返回明文；查看/复制访问 key 必须是显式操作，响应不缓存，日志不记密钥。令牌永久数据仍以 NewAPI 为准，本项目不再持久化一份访问 key 明文副本。组名、key 名称、备注和上游模型名按文本渲染，不能直接拼成可执行 HTML。

面板当前是本机控制面，只有自定义请求头作为浏览器跨域写保护，并不等于完整用户认证。新增查看完整密钥与签发能力后，首版继续限制在可信本机使用；如需远程开放，必须先设计认证授权，不能只把监听地址改成 `0.0.0.0`。

特别注意：该 NewAPI 版本允许管理员所属 token 通过特殊 key 后缀指定渠道，指定渠道路径不走普通 group/model 候选筛选。这是管理员所属 token 的特殊路由能力，不代表普通调用 key 自动拥有全部管理权限。向使用者分发的 key 应当遵守绑定组的限制，不能只在面板隐藏特殊功能就认为已经隔离。[特殊渠道权限](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/middleware/auth.go#L447)、[指定渠道路径](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/middleware/distributor.go#L32)

候选处理方式是在后端托管一个非管理员调用身份，用它签发供分发的新 token；管理员仍通过同一个面板生成、查看和撤销，不要求给每个接收者建立账号。签发身份的凭据、可用组及余额检查属于后端配置与验收内容。该方式与现有管理员名下 token 的并存、分页和权限测试留待架构阶段细化，不自动迁移或重签旧 key。

## 保持现有客户端可用的迁移方向

以下是后续实施的候选顺序，本轮不执行：

1. 将旧配置解释为一个默认 GLM 来源组，保留现有 NewAPI `default` 组标识、上游渠道 ID、访问 token、客户端 URL 和原有阈值；界面显示名称可设为“智谱主组”。
2. 先只读展示并对账旧 token 的显式组或继承组，不批量重签、不偷偷迁移访问 key，不顺便删除外部维护的渠道。
3. 新建独立火山组，配置组注册和可用权限，验证模型、鉴权和渠道状态后再生成绑定它的访问 key。尚未完成的组显示“未就绪”，不能生成看似可用的凭据。
4. 新配置及管理 API 在隔离实例验证后，再由用户确认部署和重启窗口；保存可回退的配置和数据库一致性备份。
5. 回退不仅恢复旧二进制，还要核对新增来源组、渠道和 token 的归属；不以自动删除新增资源作为回退默认动作。

旧 token 本来指向 `default` 时，继续使用原值即可；不为了把页面叫“GLM 组”而更改它的实际路由组名。

## 进入开发前的验证清单

源码与文档已确认机制可行；以下写操作和故障场景应在独立端口、独立数据库、假上游服务里验证，不拿生产 key 做错误注入：

- 两组含相同模型名，访问 key A/B 分别只进入其目标组；目标组不可用时不跨组。
- 同一访问 key 分别发送 OpenAI 与 Anthropic 格式请求，保持相同的组权限；使用者仅凭调用 key 即可使用，不需要面板会话。
- 分发的新 key 不能利用特殊渠道选择绕过组限制，也不能获得管理权限；管理员在面板仍能统一管理新旧 key。
- 两个 GLM 组可同时各有活动 key；固定或降级一组不改变另一组。
- 火山 key 不触发智谱额度探针；目录鉴权和推理鉴权独立生效；同模型的 tools、thinking、stream 另做兼容验证。
- 创建组缺注册/缺可用权限时，明确报告失败，修复后可对账恢复，不能保留隐形半成品。
- 令牌分页、生成关联、超时重试、复制、启停和删除的生命周期；普通账号不能获取或删除其他账号的 token。
- 假上游触发限额错误与慢查询，验证重试范围、固定操作的响应和真实落地状态。
- 多页面、多浏览器同时打开时，NewAPI 采集调用量不随页面数、组数成倍增长。
- 旧配置重启后仍能被原客户端使用；已有会话重登、模型发现失败保护、95% 降级和临期规则不退化。

## 待确认的首版取舍

建议按以下默认范围进入后续 workflow：

1. 支持多个来源组，每组必选 GLM 或火山；每把访问 key 固定绑定一个组，不做跨组自动兜底。
2. 两个一级页面为“来源分组”和“访问 Key”；保留现有本机管理模式，不扩展成多用户运营平台。
3. 火山先针对此前自定义 APIG，按已验证能力展示状态与组内重试，不承诺套餐额度查询或持久冷却恢复。

管理员统一管理和分发 key、使用者仅凭 key 调用、每把 key 共用两种协议的使用方式已经明确。后台签发身份属于实现取舍，不再要求用户在“自用或分发”之间选择产品模式。

候选实施顺序是：组配置和旧配置兼容 → NewAPI 分组对账与组内调度 → 火山接入适配 → 访问 key 生命周期 → 多页面整合及统一刷新。此前的暂停恢复与固定慢问题需要独立契约和回归测试，不能只通过改按钮名称掩盖；是否纳入同一开发批次在架构阶段确定。

用户确认候选方案后，再按 [workflow](../workflow.md#4-设计阶段流程) 产出架构、细化、契约审查与分步实现计划。本轮到候选方案为止，不进入业务代码实现。
