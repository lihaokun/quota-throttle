# 来源共享方案实现前审核

日期：2026-10-14。审核基线：研究稿 e1d9d39，业务代码 0b89c96。

结论：三页面、共享来源、每组独立渠道 priority 的方向可用原生 NewAPI 支撑，可以进入架构评审。此次不是全部功能实现验收，也不代表生产部署获准。逐访问 key 绑定已经取消，GLM 原有算法不改变，火山不引入临期概念。

## 本轮实证

使用生产目录中的既有二进制作为只读可执行文件，在全新临时目录、随机端口、独立 SQLite、临时账号和本机假上游中启动测试实例。没有读取生产 config.toml、生产数据库或真实 key，没有请求真实上游。测试结束后自建进程和假上游都已停止。

二进制 SHA256：90c333eb7ace489d46e25cb687767c25c3e28584ce80384f111c03ff5f5b1205。

可复现入口：[隔离契约探针](../../../scripts/probes/newapi_shared_source_probe.py)。该脚本是测试辅助工具，不是新功能的业务实现。脚本必须显式传入已有二进制路径，不下载程序，不连接现有实例。

最终运行通过 11 项检查：

1. 创建渠道时 status=2 能保持禁用。
2. CopyChannel 会继承原 group、priority、status。
3. 禁用渠道不会收到模型请求。
4. 同一来源在两个组中的不同渠道可使用不同 priority。
5. 同一访问 token 的 OpenAI 与 Anthropic 普通请求都能到正确组的首选源。
6. 改 A 组优先级不改变 B 组渠道。
7. 原生请求重试到备用不等于持久切换；下一次请求仍可回到首选。
8. 禁用同源全部渠道后，两组都改走其他可用源。
9. 批量状态请求含不存在 ID 时仍可能 success=true，必须回读。
10. 错误日志开启后，首选失败与备用成功可按 request_id 关联，同时保留实际 channel、token_id、group、model。
11. 两组共享来源、两个模型的消费记录按多个维度汇总一致。

统计样本：11 条消费记录、1 条错误记录，共 132 token；来源 S/T 分别 60/72，两个访问 token 分别 84/48，两个模型分别 120/12。重复加入同一日志再按日志 ID 去重，总量仍为 132。此样本证明字段与归属可用，不证明尚未实现的采集器能处理所有分页/迟到场景。

既有回归命令 cargo test --locked --offline -j 2：58 passed，0 failed。第一次受沙箱 Cargo 缓存只读限制未能启动编译，放行本机缓存解包后离线通过；没有更改用例以绕过业务失败。

## 必须落实的审核结论

### P1 错误计数依赖真实启用的错误日志

第一轮隔离运行有 9 条消费记录，但没有错误记录；在管理 API 写入 ErrorLogEnabled=true 无效。固定版本在 common/init.go 中从启动环境读取 ERROR_LOG_ENABLED，默认 false。补齐隔离进程的环境变量后，503 错误记录出现，且与随后成功重试保留相同 request_id。

处置：将错误遥测就绪列为火山自动状态判定的部署前提。托管启动时明确配置环境参数；已有进程不因健康就假定参数已经生效。需要重启时只能在部署获准后执行。未确认遥测能力时显示不可用/未就绪，不能把没有错误日志解释成没有失败。GLM 原服务仍可工作。

依据：[初始化开关](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/common/init.go#L156)、[错误记录路径](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/controller/relay.go#L357)。

### P1 全局状态必须是单写者并向全部成员对账

共享来源不能每组各算一次失败阈值或 token 上限，也不能由组调度器独立恢复已暂停来源。NewAPI 的自动禁用异步执行，会与我们自己的三次失败和每日重置竞争。

处置：火山业务状态由来源状态机唯一维护；受管火山渠道 auto_ban=0，由协调器显式同步 status=1/2。GLM 原 auto_ban 行为不改。恢复前先把该源各组渠道设为备用，再按组策略处理没有首选的组，防止恢复时遗留 priority=100 抢回首选。

接口 200/success 不代表全量成功，尤其批量状态接口忽略不存在的 ID，返回的是变化数量。即使数量为零也可能是目标已生效，因此不能直接比较数量判成功/失败；必须回读目标 ID 的真实状态。缺失渠道是漂移，不偷偷新建替代并改认旧历史。

### P1 配置复制必须从禁用渠道开始

CopyChannel 直接继承原组、状态和优先级，复制正在运行的首选会短暂制造原组双首选。

处置：用来源模板创建目标组的禁用渠道，保存稳定成员映射，再对账并启用。复制的是路由配置，不复制 SourceId、周期计数或异常原因。来源删除采用先停用全部成员再归档，历史映射不移交给新来源。

### P2 日志与图表必须保留联合维度和覆盖范围

现有 aggregate_usage 丢掉“时间 × 模型”联合维度；/api/data/ 没有 token/channel 维度；/api/data/flow 提供区间多维汇总但没有时间桶。不能用这些不同口径的边际汇总拼出准确 per-key 堆叠时序。

处置：统一元数据账本保留实例、日志 ID、时间、模型、token_id、channel_id 和发生时 group，再映射来源。去重、补采、检查点和聚合写入必须成组提交。图表以相同覆盖范围聚合，缺失不当作零。请求重试中的错误只供故障判断，不能作为消费计入 token。

### P2 管理 API 预算与慢请求不能挤占控制

分页补历史仍可能产生突发，即使没有逐来源轮询也会触及全局限流。现有管理客户端发送期间持有认证锁且没有总超时，新的采集量会放大控制等待风险。

处置：统一管理请求预算、显式超时、控制优先、分页检查点与退避。外部控制进度与 HTTP 回执分开，超时不宣称未执行。只对已知幂等状态写进行回读后重试，创建 token/channel 的未知结果先对账。

### P2 旧配置和新目录不能同时成为来源真值

旧配置中一把 key 对应一条渠道，不能在共享来源迁移后每次启动仍按旧 keys 重建成员；否则暂停/删除会被复活，也会重复创建渠道。

处置：显式、幂等迁移，保留旧 Source 与 default 组渠道 ID 和 token；新目录与历史映射使用独立的应用状态库。旧配置只在首次导入或明确导入操作时提供来源条目，不静默覆盖新目录。GLM 的决策参数和算法保留。

### P2 原生路由覆盖规则及组权限不能略过

探针证明的是普通 group/model/priority 路径，不包括已配置的亲和规则或管理员指定渠道。前者可能改变首选效果，后者不应作为对外签发的组隔离基础。

处置：火山组上线检查覆盖规则；新 key 使用普通签发身份、明确组并关闭跨组重试，验证越组请求失败。保留旧管理员 token 但标明权限差异，不擅自重签。组注册、可用组和渠道归属需一起对账；仍被成员或 token 引用的组不直接删除。

## 仍需在细化和实施中验证

- 实际火山网关的鉴权、SSE、tools、thinking 和错误分类；本轮仅验证假上游的普通双协议请求。
- 同 request_id 同源多次失败后成功、日志迟到、人工撤销与重置竞争时的结果归并规则，不能声称每次第三个请求返回前已同步切换。
- 非管理员签发身份的完整生命周期、配额就绪与旧管理员 token 共存；本轮路由探针使用临时管理员 token，不作为权限隔离的验收。
- 已有亲和、指定渠道规则和跨组重试的负向用例；本轮未读取或改动生产路由配置。
- API 断连、429、SQLite 写入失败、进程重启时的操作恢复，以及成员大量增加后的流控。
- 新状态机、来源管理页面、图表和迁移工具尚未实现；本轮未验收这些产品功能。
