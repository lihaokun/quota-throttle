## 1. 范围

**做**（分 5 批，每批独立可测、可部署）：

1. **用户可见修正**：组自动核验；Key 准入去掉「此刻有成员在服务」（含复制 Key）；提交被拒就地反馈；成员卡按真实原因分类；`QueueFull` 警告带调用方。
2. **去许可 + 后端检查不阻塞**：删除 `RoutingPermit` 全链路；对齐循环改为「行动时直接判断」；后端检查改为不撤销、不持锁、提交时比较代际；`mutate` 只在有变化时递增发布栅栏。
3. **火山精简 + 火山固定**：删死代码与只写不读的表；删 `error_epoch` / 证据游标 / Stale-Duplicate-Gap；去掉火山的耗尽 priority、`source_disabled`、`enable_epoch`；`cursor` 并入「上一个首选」；观测队列 + 请求阶段表改为每源一次索引查询；火山组可固定成员，固定自动解除的记录持久化（GLM 共用，§2.7）。
4. **放弃未创建的 Key**：schema v10 与第 3 批的迁移合并为一次。
5. **签发账号内部余额**（v6）：定时读余额、面板告警、手动补足、自动补足，设置可在面板修改（§2.9）；自带迁移 v9（新建 `balance_policy` 表及每个版本都要做的元数据、备份与校验链步骤，§2.9），独立上线。

**不做**：GLM 策略算法本身（阈值、临期优先、何时解除固定）不改；不加火山预防线；不改 new-api 交互协议（GET→PUT 整体搬运、管理预算）；不改面板视觉风格（火山固定按钮沿用 GLM 现有样式）。

## 2. 架构变更与跨模块不变量

### 2.1 去许可：执行依据改为「持久目标 + 当前前提」

**现状**：策略轮（GLM 10s / 火山 5s）为每个合格成员签发 ≤30s 的 `RoutingPermit`（`reconcile/planner.rs:61`）。
许可 = **策略认定合格**（GLM：`eligible` 且读数 Available；火山：`source.ready` 且在决策合格集）∩ 证据 ≤30s ∩ 后端就绪 ∩ 组就绪 ∩ 版本一致。
消费方（审核补全）：计划步骤——指令为启用时的**任何步骤（含 Confirm）**都要求许可（`planner.rs:306-311`，因此也拖延 GLM `enable_consumed`），
升优先级（`planner.rs:324-334`）与启用（`:344-352`）；`Plan::deadline`（`worker.rs:136-139`）、`can_route`（`:187-198`）、
`actionable_blocker`（`:955-961`）、执行 / 确认时的重新规划（`execution.rs:164-168`、`confirmation.rs:129-136`）；
Key 准入候选与截止（`token_service.rs:98-101,252,359`）；火山内联唤醒（`volcano_publication.rs:276-284`）。面板不读许可。

**改为**：

- 对齐循环只依据**持久化的策略目标**（`memberships.desired_priority` + `member_control.status_directive`，策略轮在事务里写入）
  加**行动当时的前提**：后端租约有效、组已就绪（**只卡启用与升优先级，从不卡停用与降级**，保持 I4）、来源未停止（暂停/退役/指令停用）、渠道观测新鲜（≤30s，原样保留）。
- **资格规则（替代许可里「策略认定合格」那一半，审核 major-1）**：只有**组策略持久记录的当前活动成员**
  （GLM `GlmGroupState.active` / 火山 `VolcanoGroupState.preferred`）才能被设为高于备用优先级；其他成员不论目标里留着什么旧值，
  对齐循环最多把它推到备用优先级。理由：策略在「未知 / 不可编辑 / 不可用」时会保留旧目标（GLM `orchestrator.rs:394-410`、
  `glm_round.rs:116-121`；火山 `volcano.rs:538-539`），旧目标可能还是 100——例如活动中被暂停、恢复后查询恰好失败。
  组决策只由有证据的策略轮写入，因此「未知当可用」的路径被堵死。
- **GLM 固定的前置条件恢复 main（v5，审查 blocker）**：生产 `decide` 在被固定成员读数缺失时直接把它设为 active（`orchestrator.rs:326-327`，
  main 的「抖动保护」）；而 SGM 的固定命令只检查 `editable`（`policy_commands.rs:44`），**允许固定一个从未查到用量的成员**。
  现在由 GLM 许可（合格 ∩ 读数 Available，`glm_publication.rs:59-66`）挡住；去许可后它会以活动优先级承接流量，且因永远没有「查到且越线」的证据而永不解除。
  main 的 `pin()` 只接受**上一轮合格集内**的成员，查询失败时拒绝（main `orchestrator.rs:493-516`）。
  改为：固定命令要求成员在**最近一次已提交且仍有效**（与面板 `current` 同一判据）的组决策合格集内，否则 `not_ready`（原因：用量未知 / 已越线 / 无有效评估）。
  固定后下一轮若该成员查询失败，仍按 main 保持它为 active——依据是不超过一轮的合格证据，与 main 相同，明示接受。
  **拒绝原因要具体**（main 的 `pin()` 会给出具体文字）：现有错误体只有 `{error, existing_source_id}`（`core.mjs:234-237`），
  因此第 2 批扩展契约：`not_ready` 可带可选枚举字段 `reason`（GLM：用量未知 / 已越线 / 无有效评估；火山：已暂停 / 已耗尽 / 运行态未初始化 / 未到周期开始 / 非 type 8 / 无渠道），
  面板据此显示具体原因，没有 `reason` 时退回第 1 步的通用文案。
- **明示接受的行为变化**：额度未知的成员现在会被以**备用优先级启用**（原先因无许可而保持停用）。这与 main（从不停用、只按 priority 分层）一致，
  且备用优先级只在活动成员失败时才可能被 new-api 回退使用。
- 升级屏障（`promotion_barrier`）原样保留，只把它需要的「备用优先级」从许可里取改为从配置取（`PlanContext.standby_priority`）。
- 火山「启用时先压到备用优先级」原样保留，同样改从配置取。
- 证据不新鲜（GLM 查询失败、火山采集停滞）时：策略轮不改目标（GLM 已是 Keep，`glm_round.rs:138`；火山不新鲜时同样不改选择），
  对齐循环继续维持既有目标——与 main「查询失败保持现状」一致。

**删除随之消失的部分**：`RoutingPermit` 类型、`Core.permits`、两处 `build_*_permits`、`wake_recovered_tx`、
火山 `SourceProjection.ready/pending`、`ledger_ready` 的**新鲜度那一半**（`initialized` 那一半仍决定运行态启动与 `selectable`，保留，`observed.rs:204-216,274`）。
`Plan::deadline` 改为只取后端到期与渠道观测到期。

**火山启用指令规则（审核 major-2）**：`Disabled` ⇐ 来源停用（耗尽 / 暂停 / 退役）；`Enabled` ⇐ 未停用 **且** `selectable`；否则不变。
规则里不含新鲜度，因此**扫描闪动问题随之消失**，不再单独修 `begin_scan`。

### 2.2 后端检查不阻塞

**现状**：`refresh_runtime_backend`（`reconcile/worker.rs:399-431`）先发布「后端不可用」，再持 `automatic_updates` 写锁做 2–4s 网络检查，
期间全部动作 NotReady、GLM 轮因 `try_read` 失败整轮作废（即 `QueueFull`）。

**改为**：读 `Core.backend_gen` → 不撤销、不持锁执行检查 → 提交：若 `backend_gen` 已变则放弃本次**成功**结果（更新的发布胜出）；
**失败结果无论如何都发布**（撤销永远安全，否则会在已知坏的后端上继续跑到 60s 租约结束）。
60s 租约起点在网络调用之前取得（`preflight.rs:332`，运行时检查沿用 `preflight/runtime.rs:51`），旧就绪仍受自身到期约束。
提交时的 `try_write` 不是为了原子性（Core 互斥已串行化），而是为了**不打断正持写锁的 Key 操作帧**
（`check_group` / Key 执行 / 复制 Key 持写锁的真实原因是阻止自动发布递增 epoch 栅栏，见 `runtime_cooperation.rs:167` 的 r7 测试）。
`observations.clear()` 与 `wake_pending` 只在就绪状态真正变化时执行。`backend_gen` 取代现有「任意发布都改 `input_epoch`」的冲突检测（`worker.rs:276,421`）。

**发布栅栏只在相关变化时递增（审核 major-3）**：栅栏是成员写（`worker.rs:529-536`）与 Key 操作帧（`token_service.rs:73-75`）共同依赖的不变量。
「相关变化」精确定义为：成员目标 / 指令、组策略状态、组就绪、成员身份或渠道绑定、后端就绪、渠道观测表的写入；
**纯账本写（事实、分钟用量单元、扫描进度）与零变化的补归属不递增**——没有任何计划或 Key 帧读取它们。细化设计逐个 `mutate` 调用点标注归类。
余额观测、补足与改设置（§2.9，v6）都不经过 `mutate`，同样不递增。

### 2.3 Key 准入（v3：用户要求「key 生成的限制也要去」）

创建 / 启用 / 复制**只保留两条硬条件**：
1. **签发账号身份与角色正确**（防止用错账号，例如管理员，去发 Key）；
2. **该组已在 new-api 登记**（签发账号能看到这个分组；未登记时 new-api 本身就会拒绝建这个分组的 Key）。

去掉的限制及理由：
- 「组里此刻有成员在服务」（v2 已去）：能否路由是会变的状态，与 Key 归属无关；
- 「组已核验就绪」：核验检查的是渠道配置，与发 Key 无关——**没核验也能提前发 Key**；
- 「签发账号 new-api 内部余额 >0」：余额只影响之后的调用，且是 new-api 内部记账、与智谱 / 火山额度无关——改为面板上提示余额不足（如何观测、提示与补足见 §2.9，v6）；
- 「组版本必须与提交时一致」：分组名不可变，绑定意义不变——**从未发出的创建自动跟上最新版本**（条件见下）。

为让「组已在 new-api 登记」在建组后立即成立，**建组时即执行注册**（只注册分组，不做渠道核验；`dispatch.rs:69`），
核验仍由 §2.4 的自动路径在渠道就位后完成。注册失败的处理必须保持 I8（§2.6，v5）。
组隔离仍由「Key 固定组 + `cross_group_retry=false`」（`newapi/tokens.rs:501-502`）及创建后核对（`tokens/execution.rs:127-141`）保证——
**但这只覆盖系统创建的 Key**：登记导入的 Key 在启用 / 复制时从不核对 `cross_group_retry`（`newapi/tokens.rs:282`）。
细化设计补上这项核对，使 I2 对导入 Key 同样成立。
从未发送的创建改绑当前组版本的条件：`create_state=never` 且没有超过 not_sent 的尝试；改绑在 prepare 事务内重新核对 `creation_allowed` 后进行；
载荷摘要保留原 `expected_group_revision`（`tokens.rs:81-107`）。

### 2.4 组就绪自动化

对齐循环在发现「组未就绪 + 已有成员渠道 + 无待处理写」时，自动执行「注册并核验」（带退避；dry_run 或无签发账号时跳过）。
**只做未就绪 → 就绪**，自动路径从不把组降为未就绪（防止来回翻转；注意未就绪→就绪本身仍会递增组版本，`groups.rs:67-71`）。手动核验入口保留。
实现约束（审核）：对齐轮次全程已持 lane（`worker.rs:992`），而 `check_group` 自己 `lane.try_lock`（`token_service.rs:321`）——需要「已持 lane」的变体；
它持写锁，会与 GLM 轮争用，故只在组未就绪时触发且带退避；注册会写全局 option，**人工拒绝（`-:group`）或 ratio/alias 不一致是终止错误**，不重试；
重试节奏服从管理预算（约 2 次/秒）。会改变 `groups_runtime_probe.py:354` 的「核验前未就绪」断言。

### 2.5 面板

- 提交被拒（收到后端明确错误且状态码不是 500 / 504，依据 I8）→ 不进操作追踪，确认框保留并就地显示中文原因；
  成功或结果不确定时关闭确认框（不确定时沿用「结果待核对」）。（v5：原写「4xx / 503」「202 才关闭」，按第 1 步细化审查精确化。）
- 轮询得到 404 → 换成「后端暂未找到这条操作记录…」的说明，**60 秒窗口内照常查询**，保留条目。
  （v5：原写「停止自动轮询」。审查指出 504 之后任务不中止，查询可能先于落库得到 404，提前停止会把晚到的提交误报为不存在。）
- 成员卡四分类：预期停止 / 待启用（附原因）/ 同步失败 / 真正意外停用；priority 不一致只在已启用且非待同步时提示。
- 访问 Key：「创建未完成：原因 · 重试 / 放弃」；已删除、已放弃收进折叠的「历史（n）」。
- 策略接管导致的 superseded 显示为「已由策略接管」，不显示成失败。

### 2.6 不变量与正确性论证

| 不变量 | 改动后由谁保证 | 论证 |
|---|---|---|
| **I1 单活动**：同组不会经确认同时存在两个活动成员 | 升级屏障 + 火山启用先压备用 | 屏障检查同组所有可能路由成员的新鲜观测（≤30s）后才允许升级；与许可无关，逻辑不变，只换备用优先级的来源 |
| **I2 不越组**：Key 只走本组渠道 | Key 固定组 + 关闭跨组重试 + 创建后核对 | 与成员是否在服务无关；无可用渠道时 new-api 返回「无可用渠道」，不会串组 |
| **I3 未知不当 0** | 资格规则：只有组决策记录的活动成员能高于备用优先级 | 策略在未知 / 不可编辑 / 不可用时会保留旧目标（可能仍是 100），所以「目标只由策略轮写入」不足以保证（v1 论证有误，审核指出）；组决策（active / preferred）只由有证据的策略轮写入，未知成员最多到备用优先级，不会抢走流量。**固定路径**（v5）：GLM 固定要求最近一次有效评估的合格证据（§2.1），火山固定要求此刻是候选（§2.7），因此固定不会把从未查到用量的成员推成活动成员 |
| **I4 停止优先** | `stopped()` / Disabled 指令先于任何启用 | 计划顺序不变：停用先执行，未知旧写先补偿（`planner.rs:296-303`） |
| **I5 后端可信** | 60s 租约 + 提交时代际比较 | 新结果不早于其证据起点；更新的发布胜出；失败仍会撤销，只是不再「先撤销再检查」。余额补足（§2.9，v6）同样只在租约有效时发送，并以租约到期为 guard；guard 只比时间，租约内的撤销（≤60s）拦不住补足，明示接受，第 2 批的 `backend_gen` 可收紧 |
| **I6 组就绪单调（自动路径）** | 自动核验只升不降 | 避免自动翻转组版本；人工核验仍可降级 |
| **I7 固定一致**（v5） | 固定命令 + 策略轮，均为 IMMEDIATE 事务并比较 `policy_revision` 后写入（`policy.rs:455-458`） | `pinned` 只能是本组未退役成员；火山只有 `pinned` 为候选时 `preferred = pinned`；「最近一次自动解除」与 `pinned` 不同时非空（解除即清 `pinned`，再固定即清记录）。策略轮写组状态时必须原样带上解除记录，否则整体比较（`policy.rs:460`）会把它清掉并多递增一次 `policy_revision` |
| **I8 首次提交被拒不留记录**（v5） | 所有写入口：校验与写入在同一事务内、提交前出错即回滚；事务外的拒绝都在调用 store 之前 | 写请求以新操作 ID 首次提交，若返回 500 / 504 以外的错误，后端没有提交任何记录（操作记录与目录行）；核验组例外（远端注册可能已做，但幂等）。面板据此就地反馈（§2.5）。**后续各步必须保持**：第 3 步「建组即注册」若注册失败，要么在提交组之前注册，要么组已提交时不以错误响应返回（例如 201 并带注册结果），否则用户重提会撞 `duplicate_group`；任何改动写路径的步骤都要扩充第 1 步的 T1。第 5 批（v6）：补足在发送前的失败什么都没做，发送后没拿到合法响应一律返回 504；改设置在事务内比较修订号；两个新路由都扩充 T1 |
| **I9 余额未知不当 0**（v6） | 余额观测（§2.9） | 读失败、或超过 3 分钟没有成功读数 → 状态为「未知」并带原因：面板显示「未知」而不是 0，自动补足不触发；不用哨兵值（负余额是真实读数）。与「任何查不到用量的路径默认未知」同一条铁律 |
| **I10 补足有界**（v6） | 补足函数 + 设置校验 | 每次补足（自动的「min(目标 − 读数, 上限)」或手动的任意金额）都在按所有者的互斥内、先查封锁、再拿到后端租约与新鲜读数之后才发送，且要求 `1 ≤ 补足量 ≤ 上限`、`读数 + 补足量 ≤ 上限`（上限 4e15）。结果不确定后，**持着同一互斥**设下封锁，10 分钟内该所有者的自动与手动补足都在第 1b 步被拒，因此同一时刻至多一笔结果不确定的补足；由于 add 在请求处理函数内同步改库（§5），下一次补足的新鲜读数必然已反映那一笔，补足后余额 ≤ 4e15。即使这条假设不成立（那一笔晚到），余额也不超过两笔之和约 8e15，仍低于 2^53−1，账号资料解析（`newapi/tokens.rs:167-170`）不会因余额过大而失败。目标是否真实存在由第 3 步的资料读取核对（rc.20 对不存在的用户 id 也回成功） |

**风险**：去许可后，策略轮刚写入目标、证据随即过期的几秒内，对齐循环仍会执行该目标——等价于 main 在两次轮询之间按上次决定行事，
单活动由屏障兜底。火山观测队列改查询涉及「请求跨清错时刻」的语义，细化设计中逐条对照现有测试。

### 2.7 火山组固定（v4 增补，用户 2026-10-29：「加」）

**现状**：只有 GLM 能固定，四处都拦着火山：
- 固定命令要求组类型为 GLM（`catalog/policy_commands.rs:36`）；
- 表约束禁止火山行写 `pinned_member_id`（`schema_v4.sql:45`），解码也拒绝（`catalog/policy.rs:385`）；
- 快照契约规定火山的 `pinned_member_id` 只能是 null（`panel-snapshot.schema.json:578`），面板只给 GLM 画按钮（`render.mjs:201`）。

火山首选目前的规则（`source_policy/volcano.rs:516-531`）是：首选仍是候选就不换；不再是候选时，按组内顺序取游标之后的下一个。
因此首选还能用时，用户无法指定改用另一个成员；唯一的绕法是暂停来源，而暂停会影响所有用到该来源的组。

**改为**：固定语义与 GLM 一致。GLM 的做法（生产实现 `orchestrator.rs:323-342`；`source_policy/reference.rs` 只是测试用的冻结副本）：
- 被固定成员在合格集内 → 生效；
- **查到且越线** → 解除并给出提示；
- 查询失败 → 保持；
- 来源暂停、来源或成员退役、成员移出组 → 在候选过滤时被静默清除（`glm.rs:97-106,121-123`）。

注意：`channel_id` 写入后从不清空（`schema_v1.sql:46-47`、`confirmation.rs:92`），所以「渠道丢失」不是一种实际存在的状态，不作为解除原因。

- **命令**：`set_group_pin` 接受火山组。
  - **前置条件是「此刻是候选」**，与选择器复用同一个判定（`volcano.rs:495-507`）：保留 `editable` 检查（`glm_round.rs:86-95`，含渠道已绑定、未暂停、未退役），
    再加未耗尽、运行态已初始化、已到周期开始、来源为 type 8，即 `observed.rs:274` 的 `selectable` 且未耗尽。
  - 运行态为 None 或来源不是 type 8 → `not_ready`。因此不会固定一个永远成不了候选的成员。
  - 不满足时按第 1 步的规则在确认框内显示原因。设为 null 表示取消固定，同时清除解除记录。
  - 已知局限：命令读的是持久化的运行态，不推进周期。每日重置后、下一轮火山策略（≤5s）之前，可能误报「已耗尽」；稍后重试即可，不为此在命令里推进周期。
- **策略轮**（`select_volcano_group`）按以下顺序处理被固定的成员：
  1. **来源暂停、来源或成员退役、移出组** → 清除固定（同 GLM），并记录原因。
  2. **来源耗尽**（达到每日上限，或连续失败熔断）→ 解除固定，并记录原因。耗尽是正面证据，对应 GLM 的「查到且越线」。
     耗尽在同一事务内、选择之前算出（`volcano_publication.rs:147-183`），所以当轮即生效。
  3. **是候选** → 设为首选（覆盖「仍是候选就不换」），游标 / 上一个首选指向它。
  4. **其他情况**（只可能是账本未初始化，或尚未到周期开始）→ 保留固定，本轮按原规则选首选；等它恢复为候选，再由固定接管。
     这一过程会切换两次（被固定成员 → 其他成员 → 被固定成员），但只在初始化或重置边界的短暂窗口内出现，明示接受。
  - **固定的生效与账本新鲜度无关**：选择器本来就不看新鲜度（`volcano_publication.rs:166`，依据 `docs/fixes/volcano-policy-fix-stale-ledger-preferred-churn.md`）。
    采集停滞时固定照样立即生效，风险与普通火山切换相同，明示接受。
  - **每日重置不恢复已解除的固定**（用户选择「自动解除」），恢复后的来源只重新成为备用候选（原规则不变）。
- **不变量**：
  - 被固定的成员只有由策略轮写入 `preferred` 后，才会高于备用优先级，而且只在它是候选（有证据）时写入。
    因此 §2.1 的资格规则与 I3 不变。
  - 切到被固定成员时走同一个升级屏障，I1 不变。
  - 固定是组级的。暂停和耗尽是来源级的，因此共享该来源的各组会各自解除自己的固定。
  - §5「组决策只由策略轮写入」仍然成立：用户命令只写 `pinned`，`preferred` 仍由策略轮决定。
- **自动解除的提示要持久**：
  - 现状：GLM 的提示只保存在内存里最近一轮的评估中，下一轮（约 10s）就消失。
    依据是 `reconcile/worker/panel.rs:252`，测试 `s6a1_imminent_reset_and_pin_release_are_last_committed_events` 断言下一轮为空。
    main 则保留到下一次手动固定或取消固定（main `orchestrator.rs:367,516`）。火山一轮只有 5s，照搬这种做法基本看不到提示。
  - 改为：在 `group_policy_state` 持久化「最近一次自动解除」，内容是成员、原因、时间，GLM 越线时再加 pct / limit。
    手动固定或取消固定时清除；GLM 与火山共用；面板横幅从快照读取。
  - 原因取值：越线（GLM）、来源耗尽（火山）、来源暂停、来源或成员退役 / 移出组。
  - GLM 的选择与解除时机不变，只是把 `glm.rs:121-123` 里没有记录的清除也记下原因。
  - 写者有两个：固定命令负责设置和清除，策略轮负责解除。两者都在 IMMEDIATE 事务里比较 `policy_revision` 后写入，见 I7。
    策略轮每次保存组状态时必须原样带上解除记录。
- **组版本**：固定命令现在无条件递增**组版本**（`policy_commands.rs:54-60`）。改为**只在 `pinned` 改变时递增**；

### 2.9 签发账号内部余额：告警 / 手动补足 / 自动补足（v6 增补，用户 2026-11-01）

**起因**：2026-11-01 12:58 本机转发全部返回 403「用户额度不足, 剩余额度: ＄-21.909360」（`native/logs/oneapi-20261021182343.log:943447`）。
new-api 按模型倍率给包月套餐虚构记账，费用从 **Key 所属用户的内部余额**里扣；Key 设为「无限额度」只免掉 Key 自己那一层，不免用户这一层。
初始化脚本给签发账号的额度是 1e12（`scripts/deploy/initialize_groups.py:303` 临时改 `QuotaForNewUser`）。本机 11 天用完（102,814 次请求，约 9e10/天）；
当时手工直写 SQLite 加了 1e15 应急。fermat 的签发账号同样是 1e12 起步。

**现状**：
- SGM 不定期观测余额。只在 Key 创建 / 启用时读一次账号资料并要求余额 >0（`reconcile/worker/token_service.rs:216`、`newapi/tokens.rs:489`）；
  §2.3 已决定去掉这条，改为「面板提示余额不足」，但没有定义怎么观测、怎么提示。
- main 在面板循环里读 `GET /api/user/self`（`orchestrator.rs:910-911`），低于 1e7 时显示红色提示（`status.rs:794,1027`）。
  按本机的消耗速率，1e7 只够十几秒，阈值不能照搬。
- Key 所有者可能有两个：签发账号与旧管理员（`runtime/config.rs:26` 的 `legacy_admin_user_id`；本机两者都配置了，分别是 `qtsigner` id 2 与 root id 1）。哪个所有者的 Key 被调用就扣哪个的余额。

**调研**（rc.20 源码 + 临时实例实测，2026-11-01；临时实例在 scratch 目录，不涉及本机数据）：
- 有正式接口：`POST /api/user/manage {id, action:"add_quota", mode, value}`（`controller/user.go:1037-1150`），`mode` 为 `add` / `subtract` / `override`。
  只有管理员能调（`AdminAuth`），且须是 root 或角色高于目标（`canManageTargetRole`，`:346-348`）。项目 CLAUDE.md「new-api 管理面没有调用户余额的 API」对 rc.20 已过时，需更正。
- `add` 是原子的 `quota + ?`，直接改库、不走批量更新（`IncreaseUserQuota(..., true)`，`model/user.go:1053-1076`）；开了 Redis 时缓存的增量由异步 goroutine 另行更新。1e15 正常。
  `value ≤ 0`、`mode` 非法、超出 int64 → `success:false`（HTTP 仍是 200）。普通用户调用被拒；root 可以给自己加。
- **陷阱**：不存在的用户 id 也返回 `success:true`，但什么都没改（`:1049-1053`：gorm `First` 未命中时不清空 Id，`Id == 0` 检查失效）；
  `id = 0` 时 gorm 忽略零值条件，`First` 直接命中 id 1（root）。⇒ 发送前必须确认目标确实存在且是本所有者（见补足函数第 3 步；`validate_owner` 已拒绝 id ≤ 0，`newapi/tokens.rs:316-318`）。
- `override` 不是原子的（与并发扣费竞争），不用。`PUT /api/user/` 的 `quota` 字段被静默忽略（与 CLAUDE.md 一致）。
- 不开 Redis 时 new-api 没有用户缓存（`model/user_cache.go:53-75`），直写 SQLite 立即生效；但开了 Redis 就不成立，而且绕过 new-api 的审计记录。⇒ **自动化只走 API。**
- SGM 解析账号资料时要求 |余额| ≤ 2^53−1（`newapi/tokens.rs:114-119,167-170`），超出则解析失败、所有 Key 操作报错。⇒ **补足必须有上界。**

**改为**（v6；§4.4 审查后修订，见 §7）：
- **观测（独立任务）**：放在 `JoinSet` 里、与 `glm_loop` 并列的独立任务，**不放进 `maintenance()`**——那是顺序循环（`runtime.rs` 的 `maintenance()`），补足的网络等待（每次请求超时 10s，429 冷却最多再等 60s）会推迟后端检查与火山策略轮。
  每 60s 读一次 `/api/status` 取换算比例，再读每个已配置所有者的资料（复用 `ManagedTokens::profile()`，身份 / 角色 / 状态核对不变）；管理预算每分钟多 2–3 次请求，可忽略。
  结果放在 worker 的独立「余额槽位」（自有互斥）：不取 `automatic_updates`、不经 `mutate`、不递增发布栅栏——没有任何计划或 Key 帧读取它，因此不会引入新的 `QueueFull`。
  任务内部的错误只记日志，不让任务退出（`runtime.rs` 的 `supervise` 在任一任务结束时停机）。
  读失败、或超过 3 分钟没有成功读数 → **未知**，并带原因（例如 `auth_failed`：账号被禁用或删除、认证熔断）（I9）。
  **不用哨兵值**：负余额是真实读数（本机曾为 −$21.9），main 的 `unwrap_or(-1)`（`orchestrator.rs:911`）不照搬。dry_run 下照常观测。
  实现约束：不用会被取消的 timeout 包住请求（重登途中被取消会熔断整个 transport，`newapi/transport.rs:907-917`）；观测不主动重试认证，避免撞上登录限流。
- **金额单位**：`quota_display_type` 为 `USD` 且 `quota_per_unit` 是正的有限数时，按美元显示与输入，与 new-api 的报错「剩余额度: ＄…」一致
  （实测 rc.20 为 `500000`、`USD`，`controller/misc.go:76-79`）；否则只显示原始额度单位，并禁用金额输入（不猜汇率与比例）。
  后端、存储与上限校验一律用原始单位；美元换成原始单位时四舍五入为整数，结果须 ≥ 1。
- **设置**（用户：「目标值和预警值是不是可以设置比较好」「自动补足不应该在 key 的设置里可以开关吗」）：三项都在面板里可改，持久化在目录库。
  - `自动补足`：开 / 关，默认开。
  - `预警线`：余额低于它就告警；自动补足开启时它也是触发线。默认 1e14（按 500000/美元约 $2 亿）。
  - `补足目标`：自动补足补到这个数。默认 1e15（约 $20 亿）。
  - 校验：`0 < 预警线 < 补足目标 ≤ 上限`，上限为 4e15 原始单位（约 $80 亿，见 I10）。设置框提示「预警线应远大于约 10 分钟的消耗」（§5）。
  - 设置是**账号级、全实例共用**的，不按 Key 或按组区分：余额属于签发 Key 的账号，所有组的 Key 共用同一份余额。配置了旧管理员时，两个所有者用同一套设置。
  - 参考：本机消耗约 9e10/天（约 $18 万/天，虚拟记账）。按默认值，从目标掉到预警线约需 27 年，所以正常运行时只有初始余额偏低的实例（例如 fermat、新装实例）会触发补足。
  - 存储：新表 `balance_policy`（单行：修订号、三项设置），迁移时写入默认行。迁移按现有机制完整进行：重建带 `CHECK(schema_version=9)` 的 `catalog_meta` 并保留实例 id、
    迁移前备份、扩展 `verify_schema` 的版本链、更新 `DATABASE_SCHEMA_VERSION` 与迁移测试（`catalog/store.rs:126-248,829-901`）。
    不写操作记录，因此不必重建操作表。这是第 5 批自己的迁移，占用 v9；原定第 3、4 批共用的迁移顺延为 v10（仍是同一次）。
  - 写入路径：改设置是同步请求，**直接持 `Core` 锁**，在 IMMEDIATE 事务内比较修订号后写入，冲突返回 `revision_conflict`；
    **不经 `mutate`**：`catalog_change` 会无条件递增栅栏并改 `input_epoch`（`reconcile/worker.rs:265-268,328-334`），那样每改一次设置都会让进行中的 Key 帧冲突、让进行中的后端检查作废。归入 §2.2「不递增」。
    写库成功后在**同一个 `Core` 临界区内**更新槽位里的设置，避免并发的两次修改以相反顺序落进槽位。
  - 启动：worker 构造时在 `Core` 内读出 `balance_policy` 写入槽位，之后才启动余额任务。
  - **锁规则**：全局顺序为「所有者异步互斥 → `Core` → 槽位」；`Core` 与槽位都是 std Mutex，绝不跨 `.await` 持有（槽位必须是 std Mutex：改设置在 bridge 的 `block_on` 里持 `Core` 时还要取它，tokio 的 `blocking_lock` 在异步上下文中会 panic）；持 `Core` 或槽位时不得等待所有者互斥。面板快照照旧 `core.try_lock()`（`reconcile/worker/panel.rs:286`）后再读槽位。
  - dry_run 下设置只读（bridge 拒绝所有写请求，`panel_http/admin/bridge.rs:79-81`）。
- **补足函数**（自动与手动共用）：
  1. 取该所有者的异步互斥：自动补足用 `try_lock`，被占就跳过本轮；手动补足等待，受路由预算约束。
  1b. **在互斥内**检查该所有者的封锁（手动与自动都查）与退避（仅自动）：命中 → 拒绝（`not_ready`，手动时提示还要等多久），什么都不做。
     封锁与退避只在持有该互斥时**写**，写时同步一份到槽位，供自动补足预筛与面板显示「还要等多久」读取；判定以这一步在互斥内读到的值为准。
  2. 短暂锁 `Core` 读后端租约：`backend.ready_at(now)` 为假 → 拒绝（`not_ready`，不计入退避，下一轮重试即可）；否则记下租约到期时刻（与 `token_frame` 相同，`reconcile/worker/token_service.rs:179-192`）。
     补足是对 new-api 的写，必须与其他写一样只在已核实的后端上执行（I5）。
  3. 读一次资料得到新鲜读数。`parse_profile` 核对返回的 id 等于所有者 id（`newapi/tokens.rs:154-165`），因此「不存在的 id 也回成功」的陷阱在这一步就被排除。
     这一步失败（含超时）也是发送之前的失败，对外映射为 `not_ready`（不能沿用 `TransportUnknown` 的 504，否则面板会误记「结果待核对」），不设封锁。
  4. 校验 `1 ≤ 补足量 ≤ 上限` 且 `读数 + 补足量 ≤ 上限`；不满足 → 拒绝（`invalid_input`）。
  5. 以「当前时刻 < min(租约到期, 手动请求的路由截止)」为 guard 发送 `add_quota add 补足量`（`send_fenced`）。不检查发布栅栏，否则任何一次发布都会让补足失败。
     并入路由截止，是为了不让面板已显示 504 之后、还在等互斥的手动任务很晚才发出 add（用户看到「结果待核对」重提就会补两次）。
     已知局限（明示接受）：guard 只比时间，租约内的撤销（≤60s）拦不住补足；第 2 批引入 `backend_gen` 后可改为同时比较后端代际。
  6. **结论只按 add 的响应判定**，不再用回读阈值（补足量小时，读数到回读之间的扣费与预扣退款会让任何阈值误判）。按传输层的投递证据（`DeliveryEvidence`）划分：
     - 没有发出（第 1–4 步的失败、guard 不满足、本地管理预算冷却造成的 429 等 NotSent）→ 明确拒绝，什么都没做；
     - HTTP 200 且 `success:true` → 已补足；
     - HTTP 200 且 `success:false` → 明确拒绝，什么都没做（rc.20 的 `success:false` 只来自处理函数正常返回：改库之前就返回，或那条 UPDATE 本身失败，`controller/user.go:1105-1121`、`common/gin.go:199-229`）；
     - 其余一律**结果不确定**（超时、连接中断、非 JSON、new-api 返回的 429 或 500 —— panic 恢复返回 500 且响应体没有 `success`，rc.20 `main.go:172-180`）：
       对外一律返回 504 `result_unconfirmed`；**持着互斥**设下该所有者的封锁，10 分钟内自动与手动补足都不再发送（I10）。
  7. 之后再读一次资料，只为刷新槽位；这次读失败不改变结论。
  发出后被拒（`success:false`）与不确定都让该所有者的自动补足退避 10 分钟；后端未就绪、读资料失败不计入退避。日志只记所有者范围、用户 id 和数字（读数、补足量、结论），不含鉴权值。
  槽位里的「上次补足结果」带来源（自动 / 手动）与时间，便于面板消解「结果待核对」。
  new-api 为每次 `add_quota` 写审计记录（`recordManageAuditFor`），作为持久痕迹。
- **自动补足**：开启、非 dry_run、槽位读数新鲜且已观测、低于预警线、不在退避期 → 调用补足函数。补足量 = min(补足目标 − **第 3 步的新鲜读数**, 上限)：读数为负、目标又设为上限时，不取 min 就会在最需要补足的「已经见底」时永远被第 4 步拒绝；读数 < 0 时补后余额 < 上限，第 4 步自然满足。新鲜读数已不低于预警线就不补。读数未知时不补（I9）。
- **手动补足**（用户：「为什么不能支持任意金额」）：**任意正金额**，输入框预填「补到目标」所需的金额，可以改成任何数；唯一的硬限制是第 4 步。
  超出时确认框就地说明；「最多还能补多少」由面板按快照读数近似计算（后端错误体只有错误码，不为此扩展字段）。
  它是同步请求（与「核验组」相同，`panel_http/admin/dispatch.rs:85`），不写操作记录。路由预算须覆盖「等待互斥 + 三次请求」；
  预算用尽时 bridge 返回 504 而任务继续执行（`panel_http/admin/bridge.rs:105-114`），面板按 504 显示「结果待核对」，并用快照里的「上次补足结果」消解。
  错误按第 1 步规则 R 就地显示：第 6 步保证「非 500 / 504 的错误 = 什么都没做」，I8 成立（§2.6）。dry_run 下拒绝。
- **状态判定**：已用完 = 读数 ≤ 0（new-api 在余额 ≤ 0 或不够预扣时返回 403，`service/pre_consume_quota.go:34-42`；余额为正但不够一次预扣时也会 403，而面板显示「偏低」，明示接受）；偏低 = 0 < 读数 < 预警线；充足 = 读数 ≥ 预警线；未知见上。
  没有配置任何所有者时 `accounts` 为空，状态栏不显示这一项。
- **面板**：
  - **各组「访问 Key」卡片顶部**（`render.mjs:218-226`）加「签发账号余额」一栏：余额、状态、读取时间、上次补足结果，以及「补足…」「设置…」两个按钮。
    该栏与设置框都写明「所有组的访问 Key 共用这个账号的余额，这里的设置对所有组生效」。配置了旧管理员时，两个所有者各占一行。
  - 顶部状态栏「后端」旁（`render.mjs:419-420`）加「内部余额」，所有页面都可见，取各所有者中最差的状态：
    充足 / 偏低（附原因：自动补足已关闭 / 上次补足失败及原因 / 退避中）/ 已用完（红色：转发会被 new-api 挡住，与智谱 / 火山额度无关）/ 未知（附原因）。

  - `PanelSnapshot`（`reconcile/worker/panel.rs:15-21`）增加 `accounts`（每个所有者一项：范围、用户 id、状态、读数、读取时间、未知原因、上次补足结果）、

**明示接受 / 不做**：
- 不改模型倍率：把倍率设为 0 可以根除扣费，但要逐个模型维护（模型目录会变，未设置的模型走默认倍率），而且改变 new-api 全局的计费语义。
- 不改初始化脚本：新装实例在第一次读数后就会被补足。
- 第 5 批部署到 fermat 后，第一次读数就会把那边的签发账号从约 1e12 补到 1e15。这是对 fermat new-api 的一次写，随部署一并确认。
- 管理员权限：后端就绪时管理员客户端必为 root（预检要读的 `/api/option/` 只对 root 开放，`newapi/managed_channels.rs:317`、rc.20 `router/api-router.go:186-187`），
  旧管理员所有者就是管理员本人（`reconcile/worker/token_service.rs:158-163`），root 可以给任何用户加额度，包括自己。权限拒绝因此不应出现；万一出现，按明确拒绝处理并在面板显示。
- 「结果不确定」的封锁只在内存里，重启后丢失。可以接受：add 在请求处理函数内同步改库，服务端处理在封锁期内结束（§5），重启通常远晚于此；重启后的第一次补足同样先取新鲜读数。
- 回读不作为结论：若该用户在第 3 步与第 5 步之间被软删除，rc.20 的 `Unscoped().First` 仍能找到它，但 UPDATE 只影响 0 行，照样回 `success:true`，结论会是「已补足」；下一次观测会读失败并显示「未知」。只有这几秒的时间差，明示接受。

## 5. 关键假设（workflow §4.2.1）

- new-api 只把请求路由到**已启用渠道中的最高 priority**，失败时按 RetryTimes=1 回退到下一档。
- 对一个渠道的写只经由**一条串行 lane**，每次写前过发布栅栏。
- 后端租约 60s、检查间隔 30s；渠道观测新鲜度 30s。
- 成员目标 / 指令只由**策略轮与用户命令**两类写者修改；组决策（active / preferred）只由策略轮写入。
- `pinned` 与「最近一次自动解除」有两个写者：固定命令（设置 / 清除）与策略轮（解除）；都在 IMMEDIATE 事务里比较 `policy_revision` 后写入（v5）。
- 一个 GLM 组同一时刻只有一个控制进程在评估；已提交的评估只存在于该进程内存，重启后需等第一轮重新产生（v5）。
- new-api 转发前按 Key 所属用户的内部余额预扣，不足即 403；Key 的无限额度不豁免这一层（2026-11-01 本机日志实测，v6）。
- `add_quota` 的语义以 rc.20 源码与实测为准；后端版本固定为 rc.20（`runtime/config.rs` 要求 `manage.version == SUPPORTED_BACKEND_VERSION`），升级 new-api 时须重跑探针（v6）。
- `add_quota add` 在请求处理函数内同步改库（`IncreaseUserQuota(..., true)`，rc.20 `model/user.go:1053-1076`）；new-api 服务端对这一请求的处理（可能晚于客户端 10s 超时）在 10 分钟封锁之内结束，因此封锁结束后的新鲜读数必然已反映那一笔（v6，I10 的前提）。I10 只约束 SGM 发起的补足；有人在 new-api 后台手工加额度不在约束之内。
- 预警线 ≫ 消耗速率 ×（60s 观测间隔 + 补足耗时 + 失败后 10 分钟退避）：默认值约有 5 个数量级的余量（本机约 9e10/天，10 分钟约 6.25e8，对 1e14）；用户把预警线设得过低时，两次观测之间仍可能见底，设置框据此提示（v6）。
